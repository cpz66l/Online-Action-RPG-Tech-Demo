# Online Action RPG Tech Demo 迭代模块规划

> 文档版本：v0.1 规划版  
> 创建日期：2026-08-13  
> 关联文档：[项目立项书](项目立项书.md)、[系统架构设计](系统架构设计.md)、[协议设计](协议设计.md)  
> 规划方式：按模块迭代，不绑定固定周数；每个迭代必须有可演示验收物

---

## 1. 迭代原则

- 先闭环，再扩展。
- 每个迭代都必须能运行、能截图、能记录问题。
- 不以“技术名词覆盖率”为目标，以“商业客户端链路可解释”为目标。
- 同一阶段只解决少数关键问题，避免登录、网络、动作、热更、Boss 同时开坑。
- AI / LLM 能力作为独立模块排在核心联机战斗闭环之后，不抢占 MVP 主链路。
- 每个迭代结束后都要补开发日志、Bug 记录和验证证据。

## 2. 迭代 0：项目骨架与通信验证

目标：客户端和服务端能连起来。

### 产出

- Unity 空工程；
- C#/.NET 服务端空工程；
- WebSocket 连接；
- `PingReq / PingRes`；
- 客户端网络日志面板；
- 服务端连接日志。

### 验收

- 启动服务端后，客户端能连接成功。
- 客户端能发送 Ping，服务端返回 Pong。
- 客户端能显示 RTT。
- 断开服务端后，客户端能显示断线提示。

### 证据

- 运行截图；
- 协议日志；
- 服务端控制台输出；
- 本阶段开发日志。

## 4. 迭代 2：大厅房间闭环

目标：多人进入同一个房间，准备并开始战斗。

### 产出

- Lobby UI；
- 房间列表；
- CreateRoom；
- JoinRoom；
- LeaveRoom；
- Ready；
- StartBattle；
- RoomStateNtf。

### 验收

- 客户端 A 创建房间。

- 两个客户端都能看到成员和准备状态。

## 10. 迭代 8：LLM 动态训练场教官 NPC

目标：在训练场中加入一个有独立模型、可行动、服务端权威同步的 AI 教官 NPC，根据玩家动作行为生成个性化战斗反馈。

定位：这是核心 MVP 闭环完成后的 AI 展示模块，不进入登录 / 大厅 / 加载 / 联机战斗主线的前置依赖。

### 技术路线

- 云端 LLM 为主，服务端通过统一 Adapter 调用，不把具体厂商写死在业务代码里。
- 服务端保留本地规则兜底，没网、超时、无 API Key 或模型返回非法结构时仍能正常给出教官反馈。
- NPC 位置、状态、交互目标、动作触发和广播由服务端权威维护。
- LLM 只生成对白、情绪、动画意图和战斗建议，不直接决定坐标、伤害、奖励或结算。
- 玩家行为先由战斗模块汇总成 `CombatObservationSummary`，再交给 NPC 模块生成反馈。
- LLM 输出必须是结构化 JSON，并经过服务端 schema / 白名单校验后再广播给客户端。

### 产出

- 训练场教官 NPC Prefab，包含模型、基础待机 / 走路 / 说话 / 指示动作。
- NPC 场景行为：Idle、Patrol、LookAtPlayer、Talking、Cooldown。
- 服务端 `NpcService`，维护 NPC 权威状态和交互状态。
- NPC 同步协议：NpcSpawnNtf、NpcStateNtf、NpcActionNtf、NpcTalkReq / NpcTalkRes。
- 客户端 NpcAgent：接收服务端状态，驱动 NavMeshAgent / Animator 表现。
- 玩家靠近交互与对话 UI。
- 玩家行为观察摘要：受击次数、闪避时机、技能使用频率、训练结果等。
- 云端 LLM Adapter：通过 `baseUrl`、`apiKey`、`model`、`timeoutMs` 配置接入。
- RuleBased fallback：根据行为摘要生成固定但合理的教官反馈。
- NPC Debug 信息：NPC 状态、最近观察摘要、LLM 耗时、fallback 原因。

### 验收

- 两个客户端进入训练场后，都能看到同一个服务端权威 NPC。
- NPC 能在训练场内巡逻、待机，并在玩家靠近时转向玩家。
- 玩家可与 NPC 交互并触发对话。
- 玩家发生典型行为后，NPC 能给出对应反馈，例如过早闪避、承受过多伤害、长时间不用技能、训练完成。
- 云端 LLM 可用时，NPC 返回自然语言反馈和结构化意图。
- 云端不可用时，RuleBased fallback 能无感接管，客户端仍可完成交互演示。
- LLM 返回非法 JSON 或非法意图时，服务端拒绝执行并回退到安全回复。
- 客户端不保存 LLM API Key，不直接调用云端模型。

### 证据

- NPC 场景行动录屏。
- 双客户端 NPC 同步录屏。
- 玩家行为摘要日志。
- LLM 请求耗时和 fallback 日志。
- 云端可用 / 断网兜底两种演示截图或录屏。
- NPC 协议日志和 Debug 面板截图。

### 暂不做

- 不做完整剧情、任务链或开放世界 NPC 生态。
- 不让 LLM 直接控制 NPC 高频移动、战斗判定、奖励和结算。
- 不在战斗每帧或每次攻击时调用 LLM。
- 不同时接入多个不同人设 NPC，第一版只做训练场教官。
- 不把本地大模型部署作为第一版硬依赖。

## 12. 迭代 10：加分扩展候选

本阶段只在 MVP 完成后选择 1-2 个高价值方向，不同时展开。

| 扩展 | 价值 | 风险 |
|---|---|---|
| SQLite 持久化 | 展示账号数据落盘 | 后端时间增加 |
| MessagePack / Protobuf | 展示协议工程化 | 需要协议生成或映射维护 |
| KCP / UDP | 更接近实时同步讨论 | 调试复杂度上升 |
| 客户端预测 | 同步面试加分 | 难度高，容易拖慢项目 |
| xLua 数据 / 技能热更 | 国内商业项目常见 | 不宜过早接入 |
| 简单 Boss | 提升演示观感 | 容易变成玩法项目 |
| 技能 Shader / 特效 | 靠近动作 RPG 表现 | 需要图形学和美术时间 |
| 多 NPC 与人设系统 | 展示 AI 内容扩展能力 | 容易膨胀成剧情系统 |
| 本地 LLM 兼容接口 | 展示离线和私有化部署思路 | 模型部署与效果调优成本较高 |

每个迭代结束后必须补充：

- 协议或架构变更；

- 下一迭代风险。

这些材料后续应整理进 `C:\Users\cp\knowledge-base` 的学习区和正式知识页面。
