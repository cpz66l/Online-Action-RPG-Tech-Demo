## 1. 协议目标

MVP 协议设计遵循以下原则：

- 请求、响应、广播分清楚。
- 每个请求都有 `requestId`，方便匹配响应和超时。
- 每个消息都有 `msgId` 和 `type`，方便日志定位。
- 第一版使用 JSON，便于调试和展示。
- 后续可替换为 MessagePack / Protobuf，不改变业务语义。

## 2. 基础包结构

### 2.1 Client -> Server 请求

```json
{
  "msgId": 1001,
  "type": "LoginReq",
  "requestId": "uuid",
  "token": "",
  "clientTime": 123456,
  "payload": {}
}
```

### 2.2 Server -> Client 响应

```json
{
  "msgId": 1002,
  "type": "LoginRes",
  "requestId": "uuid",
  "code": 0,
  "message": "OK",
  "serverTime": 123999,
  "payload": {}
}
```

### 2.3 Server -> Client 广播

```json
{
  "msgId": 3001,
  "type": "RoomStateNtf",
  "serverTime": 123999,
  "payload": {}
}
```

## 3. 通用字段

| 字段 | 方向 | 类型 | 说明 |
|---|---|---|---|
| `msgId` | 双向 | int | 消息编号 |
| `type` | 双向 | string | 消息类型，便于日志阅读 |
| `requestId` | 请求 / 响应 | string | 请求唯一 ID，用于匹配响应 |
| `token` | Client -> Server | string | 登录后的会话凭证 |
| `code` | Server -> Client | int | 结果码，0 表示成功 |
| `message` | Server -> Client | string | 错误或提示信息 |
| `clientTime` | Client -> Server | long | 客户端时间戳，用于 RTT / 调试 |
| `serverTime` | Server -> Client | long | 服务端时间戳 |
| `payload` | 双向 | object | 具体业务数据 |

## 4. 错误码

| code | 含义 | 说明 |
|---:|---|---|
| 0 | OK | 成功 |
| 1001 | 参数错误 | 缺字段、非法值或格式错误 |
| 1002 | 未登录 | 请求需要 Token 但未提供 |
| 1003 | Token 失效 | Token 过期或无法识别 |
| 1004 | 请求超时 | 客户端或服务端等待超时 |
| 2001 | 账号已存在 | 注册时用户名重复 |
| 2002 | 账号或密码错误 | 登录失败 |
| 3001 | 房间不存在 | Join / Ready / Start 指定房间无效 |
| 3002 | 房间已满 | 房间人数达到上限 |
| 3003 | 状态不允许 | 未准备、非房主、战斗中等 |
| 4001 | 战斗不存在 | 战斗实例无效 |
| 4002 | 非法战斗操作 | 技能不存在、角色死亡后操作等 |
| 9001 | Debug 命令无效 | GM 或调试请求无效 |

## 5. 消息编号规划

| 范围 | 模块 | 示例 |
|---:|---|---|
| 1000-1999 | Account | Register / Login / Heartbeat |
| 2000-2999 | Lobby | EnterLobby / RoomList |
| 3000-3999 | Room | CreateRoom / JoinRoom / Ready / StartBattle |
| 4000-4999 | Loading | LoadProgress / BattleReady |
| 5000-5999 | Battle | Input / Snapshot / Event / Result |
| 9000-9999 | Debug | Ping / GM / LatencySim |

payload：

```json
{
  "latencyMs": 120,
  "jitterMs": 30,
  "packetLoss": 0.05
}
```

### 10.3 GmCommandReq

payload：

```json
{
  "command": "add_hp",
  "args": {
    "value": 50
  }
}
```

候选命令：

- `add_hp`；
- `kill_self`；
- `reset_battle`；
- `spawn_dummy`；
- `force_result`。

## 11. 同步策略约定

MVP 同步策略：

- 位置、朝向和基础状态由服务端快照广播。
- 远端玩家由客户端插值显示。
- 本地玩家可以先播放动作，提高响应感。
- 伤害、血量、死亡和结算以服务端广播为准。
- 技能释放先以事件同步，不做复杂回滚。
- 所有快照和事件都写入 Debug 日志，便于面试展示和问题复盘。

后续升级路线：

- JSON -> MessagePack / Protobuf；
- WebSocket -> KCP / UDP；
- 快照同步 -> 客户端预测 / 服务端校验；
- 普通日志 -> 协议录制与回放；
- 位置同步 -> 插值参数可视化和弱网测试报告。

## 12. 协议验收标准

- 登录协议能完整走通成功和失败分支。
- 房间协议能完整走通创建、加入、准备、开始、退出。
- 加载协议能记录每个客户端加载进度和 Ready 状态。
- 战斗协议能同步移动、动作、受击、血量、死亡和结算。
- Debug 面板能显示最近协议包、RTT 和当前房间 / 战斗状态。
- 所有错误码都能在客户端显示可理解提示。
