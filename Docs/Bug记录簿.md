## BUG-001：普攻“打不出伤害”，实际命中一直在生效

- 发现日期：2026-09-11
- 所属模块：战斗 / UI
- 严重程度：高
- 现象：作者反馈操控玩家攻击训练木桩时“不能造成伤害”，木桩没有任何视觉反馈，看起来像命中判定完全没有工作。
- 排查过程：先读 Unity Editor 日志，发现最近一次试玩中已有 8 条 `[Combat] Hit ... for 12` 和对应的 `HP=88/100` 到 `4/100` 记录，调用栈完整经过 `HitBox.FixedUpdate -> ResolveHit -> HurtBox.TryReceiveHit -> TrainingDummy.ApplyDamage`，说明伤害链路本身是通的。
- 根因：木桩的 HP 显示是一个 World Space Canvas，作为子物体拖入时没有清零 `localPosition`，其局部 z 恰好等于根节点的世界 z；父节点又被旋转了 180°，导致这个 Canvas 落到了玩家出生点脚下的地面，距离木桩约 8 米。同时木桩当时还没有受击动作，所以打上去在观感上“什么都没有发生”。
- 修复方案：把 Canvas 移到木桩头顶，并缩小到合理尺寸；后续补充木桩受击动作。
- 验证方式：普攻后木桩头顶 HP 文本可见且随命中下降，日志数值与显示一致。
- 沉淀规则：**“看不到反馈”和“没有生效”是两件事。** 排查表现类问题时，先确认事实层是否成立，再去看表现层；顺序反了会在错误的层反复怀疑。
- 是否已回归：是

## BUG-002：木桩开局显示 HP 0 / 100

- 发现日期：2026-09-11
- 所属模块：战斗 / UI
- 严重程度：中
- 现象：进入训练场时木桩头顶显示 `HP 0 / 100`，第一次命中后数值恢复正常。
- 排查过程：对比显示初始化和木桩状态初始化的执行时机，确认文本组件先于木桩组件执行。
- 根因：`TrainingDummyHpDisplay.Awake()` 中调用 `Refresh()` 读取 `dummy.CurrentHp`，而 `CurrentHp` 是在 `TrainingDummy.Awake()` 中才被赋成 `maxHp` 的。Unity 不保证不同 GameObject 之间 `Awake` 的执行顺序，这里恰好是“先文本、后木桩”，于是读到了 `float` 的默认值 0。
- 修复方案：把初始刷新从 `Awake()` 移到 `Start()`。`Start` 一定在所有 `Awake` 之后执行。
- 验证方式：进入训练场后木桩立即显示 `100 / 100`；命中后数值正常递减。
- 沉淀规则：**不要在一个组件的 `Awake` 里读取另一个组件的运行时状态**，除非用 `[DefaultExecutionOrder]` 显式固定顺序。跨脚本读状态要么放 `Start`，要么走事件。
- 是否已回归：是

## BUG-003：木桩死亡动画躺在半空

- 发现日期：2026-09-11
- 所属模块：战斗 / 动画
- 严重程度：中
- 现象：木桩 HP 归零播放死亡动画时，躺倒动作在空中进行，身体没有贴地。
- 排查过程：确认木桩根节点位置在世界空间中保持不动，问题出在动画表现层而不是位移逻辑；进一步检查 FBX 片段设置，发现各片段的 `Bake Into Pose` 配置一致，但只有 `Death01` 的垂直位移量较大。
- 根因：`TrainingDummyAnimatorDriver` 为了让木桩位置保持权威，在 `Awake` 里关闭了 `animator.applyRootMotion`。Humanoid 重定向下，片段垂直位移的去处取决于 `Bake Into Pose`：未勾选时位移被抽成 root motion，勾选后才留在骨骼姿势里。`Death01` 的“下沉”原本在 root motion 中，关掉之后整段位移被丢弃——姿势躺下了，根节点还站在原高度。
- 修复方案：在 FBX 导入设置中为 `Death01` 勾选 `Root Transform Position (Y)` 的 `Bake Into Pose`，让死亡片段变为完全 in-place，同时保持 `applyRootMotion = false`。
- 验证方式：木桩死亡时身体贴地躺倒，根节点位置不变；复活后姿态正常。
- 沉淀规则：**“让动画不影响位移”和“让动画把角色放倒在地上”是两个相反的需求。** 决定关闭 Root Motion 之前，先确认目标片段的关键位移是烘焙在姿势里还是抽成了 root motion；死亡、翻滚、位移技能这类大幅位移片段要单独确认。
- 是否已回归：是

## BUG-004：锁定日志的方向和判定用的方向不一致

- 发现日期：2026-11-01
- 所属模块：战斗 / 调试工具
- 严重程度：中
- 现象：04F-1 中键选目标的调试日志里，`angle` 长期落在 87°–173°，看起来像“背对目标也能锁定”，与“按视角选目标”的设计不符。
- 排查过程：对比 `SelectTarget` 与 `LogSelection` 的 forward 来源，发现选择用 `_cameraTransform.forward`，日志用 `transform.forward`；同时 `toTarget` 带 y 分量，而 forward 已压平，`Vector3.Angle` 把高度差也算进了正面夹角。
- 根因：调试输出另算了一遍输入，而不是复用判定逻辑的输入；角度计算混入了垂直分量。
- 修复方案：提取 `ResolveSelectionForward()` 供选择与日志共用；角度改用水平化后的 `flatToTarget`；`TargetSelector` 同步修正，并把“目标在正上方”的边界判断改为按水平距离。
- 验证方式：修复后同一场景下 `angle` 从 87°–173° 降到 25°–47°；相机正对、角色背对时 angle 接近 0。
- 沉淀规则：**调试输出必须复用判定逻辑的输入。** 日志另算一遍，会在错误的地方给出“看起来合理”的数字，比没有日志更难排查。另外，凡是用 `Vector3.Angle` 计算“正面夹角”，先确认两个向量是否在同一平面。
- 是否已回归：是
