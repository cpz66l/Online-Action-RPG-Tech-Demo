## 7. 协议建议

建议在实现前先固定命名约定：

- `Req / Res`：明确请求-响应，必须带 `requestId`。
- `Ntf`：服务端主动通知或广播，一般不需要 `requestId`。
- `Cmd`：客户端发送的高频或行为命令，可以无响应，例如 `PlayerInputCmd`。

建议调整或确认的点：

- `LoadBattleSceneRes` 更像服务端主动通知，建议改名为 `StartLoadingNtf` 或 `LoadBattleSceneNtf`。
- `ClientLoadProgressNtf` 是客户端上报，若坚持严格语义，建议改成 `ClientLoadProgressReq` 或 `LoadProgressCmd`。
- `PingReq / PingRes` 和 `HeartbeatReq / HeartbeatRes` 要分工：Ping 用于调试 RTT，Heartbeat 用于连接保活。
- `msgId` 和错误码当前都使用类似数字区间，例如 `3001` 既可能是房间消息也可能是房间错误码；字段不同可以工作，但日志显示时要明确前缀。

## 8. 推荐下一步

### 迭代 0 目标

只做一件事：让 Unity 客户端和本地 C# 服务端通过 WebSocket 完成 Ping / Pong，并在客户端显示连接状态、RTT 和最近协议日志。

### 建议任务顺序

1. 初始化 Git 仓库，添加 Unity / .NET `.gitignore`。
2. 确认 Unity Editor 版本，创建 `Client/UnityProject/`。
3. 创建 `Server/OnlineRpgServer/`，优先用 Console 服务端，减少 ASP.NET 初期复杂度。
4. 固定服务端 SDK / target framework。
5. 定义第一批共享协议 DTO：`Envelope`、`PingReq`、`PingRes`、`ErrorRes`。
6. 服务端实现 WebSocket accept、连接日志、Ping 处理。
7. 客户端实现连接按钮、发送 Ping、显示 RTT、断线提示。
8. 在 `Docs/开发日志/` 新建迭代 00 日志，记录运行截图、控制台输出和问题。

## 9. 阶段性判断

当前最值得做的不是继续设计“完整动作战斗”，而是尽快建立第一条可运行证据链。只要迭代 0 跑通，这个项目就会从“规划文档”进入“真实工程”，后续每个模块才能开始积累可截图、可录屏、可复盘的求职证据。
