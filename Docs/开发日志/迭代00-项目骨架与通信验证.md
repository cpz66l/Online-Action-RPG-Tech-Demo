## 5. 设计取舍

### 为什么先做 Ping / Pong

Ping / Pong 是联网链路里最小、最清楚的可验证闭环。它不涉及账号、房间、战斗状态，也不依赖复杂 UI，因此可以优先验证：端口监听、WebSocket 握手、JSON 包结构、请求响应匹配、RTT 统计和日志输出。

### 为什么先用 WebSocket + JSON

MVP 阶段优先可读、可调试、可截图。JSON 包能直接在日志面板和服务端控制台展示，适合作品集解释。后续如果要扩展 MessagePack / Protobuf，应该保持业务语义不变，只替换序列化层。

### 为什么先不做登录

登录需要账号状态、错误码、Token、UI 状态切换和持久化边界。它建立在基础通信已经可靠的前提上。先完成 Ping / Pong，可以避免把“连接失败”和“登录业务失败”混在一起排查。

### 动作 RPG 网络路线对齐

本项目是动作 RPG 技术 Demo，后续战斗同步会遇到 TCP 队头阻塞问题。当前路线不是把 WebSocket 作为最终强实时同步方案，而是按阶段推进：

```text
阶段 A：WebSocket + JSON MVP
  -> 登录 / 大厅 / 房间 / 加载 / Ping / Debug
  -> 先跑通商业客户端链路
  -> 保留协议日志和可视化调试证据

阶段 B：同步表现优化
  -> 服务端 Tick
  -> BattleSnapshotNtf
  -> 远端角色插值缓冲
  -> sequence / serverTime
  -> 过期快照丢弃
  -> 弱网模拟和网络状态面板

阶段 C：加分扩展
  -> 继续 WebSocket，但替换为 MessagePack / Protobuf
  或
  -> 拆分可靠通道和实时通道：WebSocket 负责登录 / 大厅，UDP / KCP 负责战斗同步
```

当前实现策略：

- 第一版仍使用 WebSocket + JSON，优先完成端到端链路和调试证据。
- Unity 客户端网络层后续应预留 `INetworkTransport` 抽象，业务层不直接依赖 WebSocket API。
- 可靠业务消息继续适合 WebSocket，例如登录、房间、准备、开始、结算。
- 高频实时状态后续可评估 UDP / KCP，例如位置快照、朝向、移动状态和输入命令。
- 不在 MVP 早期同时展开 MessagePack、KCP、预测、回滚，避免拖慢主线。

后续 Unity 客户端网络层建议分层：

```text
UI / Gameplay / Sync
        |
NetworkClient
        |
ProtocolCodec / ProtocolRouter
        |
INetworkTransport
        |
WebSocketTransport
```

面试表达边界：

> 当前 MVP 使用 WebSocket + JSON 跑通基础通信链路，并计划通过 Transport 抽象为后续 KCP / UDP 战斗通道预留替换空间。当前还没有实现 UDP / KCP，也没有完成客户端预测或回滚。
