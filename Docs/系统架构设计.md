# Online Action RPG Tech Demo 系统架构设计

> 文档版本：v0.1 规划版  
> 创建日期：2026-08-13  
> 关联文档：[项目立项书](项目立项书.md)、[协议设计](协议设计.md)、[迭代模块规划](迭代模块规划.md)  
> 架构原则：MVP 先跑通商业客户端纵切链路，后续再做高阶同步、热更新和表现扩展

---

## 1. 架构目标

本项目的系统架构服务于三个目标：

1. 展示商业游戏客户端常见流程：登录、大厅、房间、异步加载、战斗、结算、回流。
2. 展示客户端与服务端职责分离：客户端负责输入、表现、UI、资源和预测展示；服务端负责账号、房间、战斗权威状态和广播。
3. 保持可落地：先完成 2 客户端 + 1 本地服务端的最小联机动作 RPG Demo，再扩展协议、同步和工具。

## 2. 总体架构

```text
Unity Client
  App / Boot
  UI Flow
  Network
  Resource
  Gameplay
  Combat
  Sync
  Debug
      |
      | WebSocket / JSON MVP
      v
C#/.NET Server
  Connection / Gateway
  Account
  Lobby / Room
  Battle
  Protocol
  Persistence
  Debug
```

### 2.1 客户端职责

- 展示 UI 流程和交互反馈。
- 采集本地输入并发送协议。
- 维护本地表现状态和远端角色插值表现。
- 管理 Addressables 异步加载、资源句柄和卸载。
- 播放动作、技能、受击、特效、音效和 HUD。
- 提供网络日志、状态面板、延迟 / 丢包模拟等调试工具。

### 2.2 服务端职责

- 维护连接、会话、心跳和 Token 校验。
- 处理注册、登录、大厅、房间和准备状态。
- 创建战斗房间，按 Tick 处理输入、广播快照和战斗事件。
- 维护权威血量、死亡、战斗开始和结算。
- 输出服务端日志，辅助排查协议和状态问题。

## 3. 客户端分层设计

### 3.1 App / Boot 层

职责：

- 启动客户端；
- 初始化配置、日志、资源系统和网络模块；
- 管理 `AppState`；
- 决定进入 Login、Lobby、Loading、Battle 或 Error 状态。

MVP 内容：

- `BootScene` 或启动入口；
- `AppController`；
- 基础日志；
- 全局状态切换。

边界：

- Boot 层不处理具体业务协议。
- Boot 层不直接控制战斗角色。

### 3.2 UI Flow 层

职责：

- Login UI；
- Lobby / Room UI；
- Loading UI；
- Battle HUD；
- Result UI；
- 错误弹窗和重连提示。

边界：

- UI 只发出用户意图，不直接修改服务端权威状态。
- UI 不直接解析网络包，由业务 Controller 接收网络事件后刷新 UI。

### 3.3 Network 层

职责：

- WebSocket 连接；
- 协议序列化 / 反序列化；
- 请求 / 响应匹配；
- 广播分发；
- 心跳；
- 断线提示；
- 网络日志和 RTT 统计。

核心对象建议：

| 对象 | 职责 |
|---|---|
| `NetworkClient` | 建立连接、发送、接收、断线处理 |
| `ProtocolRouter` | 按 `msgId` 或 `type` 分发消息 |
| `RequestTracker` | 匹配 `requestId`、超时和回调 |
| `NetworkDiagnostics` | RTT、丢包模拟、协议日志 |

边界：

- Network 层不持有 UI 引用。
- Network 层不理解技能、房间或角色具体业务，只负责通信和分发。

### 3.4 Resource 层

职责：

- Addressables 初始化；
- 配置表加载；
- 场景异步加载；
- 角色、技能、特效、UI 资源加载；
- 加载进度和失败重试；
- 资源句柄释放。

MVP 目标：

- 登录后加载大厅需要的 UI / 配置；
- 开始战斗时加载训练场、角色 Prefab、技能特效；
- Loading UI 能显示真实进度，而不是纯假进度条。

边界：

- Resource 层不写业务规则。
- 资源所有权必须明确：谁加载，谁释放；全局资源和战斗局内资源分开。

### 3.5 Gameplay 层

职责：

- 本地玩家控制；
- 远端玩家表现；
- 角色基础状态；
- 移动、朝向、锁定、动画参数；
- 从同步层接收远端状态。

MVP 内容：

- 第三人称移动；
- 镜头跟随；
- 目标锁定；
- 本地玩家和远端玩家区分；
- 远端玩家插值显示。

边界：

- 本地玩家由输入驱动。
- 远端玩家由网络同步状态驱动。
- Gameplay 不直接改服务端权威血量。

### 3.6 Combat 层

职责：

- 普攻；
- 闪避；
- 技能；
- CD；
- HitBox / HurtBox；
- 受击；
- 伤害事件；
- 死亡表现。

MVP 决策：

- 客户端可以先播放本地动作表现。
- 伤害、血量和死亡以服务端广播为准。
- 第一版不做复杂预测和回滚。

### 3.7 Sync 层

职责：

- 接收服务端快照；
- 管理远端玩家状态缓冲；
- 插值位置和朝向；
- 播放战斗事件；
- 同步血量、死亡、结算。

MVP 同步策略：

```text
Local Input / Action
  -> Send Command
  -> Server Tick
  -> Snapshot / Event Broadcast
  -> Remote Interpolation / Event Playback
```

边界：

- Sync 层不负责 UI 布局。
- Sync 层不加载资源，只请求 Resource 层提供需要的 Prefab 或特效。

### 3.8 Debug 层

职责：

- 网络包日志；
- RTT 显示；
- 延迟 / 丢包模拟；
- 玩家状态面板；
- 房间状态面板；
- GM 指令；
- 同步插值参数显示。

面试价值：

- 证明同步问题可观察；
- 证明不是只做出“看起来能跑”的 Demo；
- 为后续性能和弱网测试留下证据。

## 4. 服务端分层设计

### 4.1 Connection / Gateway

职责：

- 监听客户端连接；
- 维护 `ConnectionId`；
- 绑定 `PlayerSession`；
- 接收协议并转发业务模块；
- 心跳和断线检测。

### 4.2 Account

职责：

- 注册；
- 登录；
- Token 生成；
- Token 校验；
- 玩家基础资料。

MVP 持久化：

- 第一版可以使用内存字典。
- 后续接 SQLite，展示简单持久化能力。

### 4.3 Lobby / Room

职责：

- 进入大厅；
- 房间列表；
- 创建房间；
- 加入房间；
- 离开房间；
- 准备状态；
- 房主开始战斗。

权威状态：

- 房间是否存在；
- 房间人数；
- 谁是房主；
- 谁已准备；
- 是否允许进入战斗。

### 4.4 Battle

职责：

- 创建战斗实例；
- 分配出生点；
- 接收玩家输入和行为命令；
- 按 Tick 更新权威状态；
- 广播快照和战斗事件；
- 判断死亡和结算。

MVP 决策：

- 服务端先不做复杂物理模拟。
- 服务端至少维护位置、朝向、血量、战斗状态和事件顺序。
- 后续再扩展服务端校验和反作弊边界。

### 4.5 Protocol

职责：

- 消息编号；
- 请求 / 响应 / 广播结构；
- 错误码；
- 序列化；
- 协议文档同步。

### 4.6 Persistence

职责：

- 账号数据；
- 玩家基础资料；
- 后续可扩展战斗记录。

MVP：

- 内存数据即可。
- 不把数据库设计作为第一阶段重点。

### 4.7 Debug

职责：

- 连接日志；
- 请求日志；
- 房间日志；
- 战斗 Tick 日志；
- 快照广播日志；
- 错误码统计。

## 5. 关键状态流

### 5.1 启动流

```text
Launch Client
  -> Boot
  -> Load Local Config
  -> Init Addressables
  -> Init Network Client
  -> Show Login UI
```

### 5.2 登录流

```text
Input Username / Password
  -> LoginReq
  -> Server Validate
  -> LoginRes(token, playerId, nickname)
  -> Save Session
  -> Enter Lobby
```

### 5.3 房间流

```text
Enter Lobby
  -> CreateRoom / JoinRoom
  -> RoomStateNtf
  -> ReadyReq
  -> RoomStateNtf
  -> StartBattleReq(owner only)
  -> LoadBattleSceneRes
```

### 5.4 加载流

```text
Server Allows Loading
  -> Client Load Config
  -> Load Battle Scene
  -> Load Character Resources
  -> Load Skill VFX
  -> ClientLoadProgressNtf
  -> ClientBattleReadyReq
  -> BattleStartNtf
```

### 5.5 战斗流

```text
Local Input
  -> PlayerInputCmd / PlayerActionCmd
  -> Server Tick
  -> BattleSnapshotNtf
  -> BattleEventNtf
  -> Client Render Local / Remote State
```

### 5.6 结算流

```text
Battle End Condition
  -> Server Generate Result
  -> BattleResultNtf
  -> Result UI
  -> Return Lobby
  -> Release Battle Resources
```

## 6. 客户端状态机

```text
Boot
  -> Login
  -> Lobby
  -> Loading
  -> Battle
  -> Result
  -> Lobby
```

异常状态：

- `Reconnecting`：断线重连中；
- `Error`：无法恢复的错误；
- `Disconnected`：连接断开，返回登录或大厅；
- `LoadingFailed`：资源加载失败，允许重试或返回大厅。

## 7. 场景规划

| 场景 / 面板 | 作用 | MVP 形式 |
|---|---|---|
| BootScene | 初始化入口 | 独立场景或首场景空对象 |
| LoginPanel | 登录 / 注册 | UI 面板 |
| LobbyScene | 大厅 / 房间 | 独立场景或 Lobby Panel |
| LoadingPanel | 加载进度 | 覆盖式 UI |
| BattleArenaScene | 战斗训练场 | 独立场景 |
| ResultPanel | 结算 | 覆盖式 UI |

## 8. 数据所有权

| 数据 | 权威方 | 客户端是否缓存 | 说明 |
|---|---|---|---|
| 账号密码 | 服务端 | 不保存明文 | MVP 可简化，仍避免在客户端长期保存密码 |
| Token | 服务端生成 | 客户端保存本次会话 | 用于请求认证 |
| PlayerProfile | 服务端 | 客户端缓存 | 昵称、playerId 等基础信息 |
| RoomState | 服务端 | 客户端显示缓存 | 房间列表、成员、准备状态 |
| BattleState | 服务端 | 客户端表现缓存 | 战斗开始、结束、玩家权威状态 |
| LocalInput | 客户端 | 本地短暂缓存 | 发送给服务端，用于表现和同步 |
| SkillConfig | 客户端资源 / 配置 | 客户端缓存 | 后续可做配置热加载 |
| HP / Death | 服务端 | 客户端显示缓存 | 以服务端广播为准 |
| ResourceHandle | 客户端 | 客户端维护 | 谁加载谁释放 |

## 9. 模块依赖原则

- UI 不直接改战斗事实，只发送用户意图。
- Gameplay 不直接解析网络包，只接收业务事件或同步状态。
- Network 不持有 UI 引用，只负责连接、收发和分发。
- Resource 不写业务规则，只提供加载、卸载和进度。
- Combat 不直接管理房间和账号。
- Sync 不生成权威战斗结果，只表现服务端状态。
- Server 不负责表现，只维护权威状态和广播事件。

## 10. MVP 验收标准

- 2 个客户端可以连接同一个本地服务端。
- 两个账号可以注册 / 登录。
- 一个客户端创建房间，另一个客户端加入房间。
- 两个客户端都能准备，房主开始战斗。
- 客户端异步加载战斗场景，加载完成后上报服务端。
- 两个客户端进入同一战斗场景。
- 本地玩家能移动、普攻、释放 1 个技能。
- 远端玩家位置、朝向、动作事件和血量能同步显示。
- 战斗能结算，并回到大厅。
- Debug 面板能显示连接状态、RTT、最近协议包和玩家状态。
