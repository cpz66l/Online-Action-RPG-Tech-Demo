# Online Action RPG Tech Demo 项目立项书

> 文档版本：v0.1 立项版  
> 创建日期：2026-08-13  
> 项目状态：规划中，预计在《背包幸存者》v0.3 完成后启动  
> 项目定位：面向游戏客户端开发实习求职的联机动作 RPG 客户端技术纵切 Demo  
> 当前原则：先做小而完整的商业客户端流程，不做大而散的技术拼盘

---

## 1. 项目一句话

开发一个 Unity 联机动作 RPG 技术 Demo，覆盖账号登录、大厅房间、异步资源加载、第三人称动作战斗、客户端与服务端网络同步、调试工具、性能记录和演示交付，用来展示接近商业游戏客户端工作流的工程能力。

---

## 2. 项目背景

第一个主推项目《背包幸存者》已经重点展示了：

- 单机 Demo 可玩闭环能力；
- 玩法系统架构深度；
- 纯 C# 背包、邻接构筑、掉落经济、波次导演、对象池等系统设计；
- 真实 Bug 复盘、性能取舍和 Windows Build 交付。

第二个项目不再重复证明“能做一个完整单机玩法 Demo”，而是补齐另一条求职证据链：

```text
商业客户端入口
  -> 账号 / 大厅 / 房间
  -> 异步资源加载
  -> 联机战斗场景
  -> 网络同步
  -> 调试工具
  -> 性能与交付证据
```

它的核心价值是证明：我不仅能做玩法系统，还理解真实客户端项目中常见的账号、资源、网络、场景流、动作战斗、工具和性能验证流程。

---

## 3. 项目目标

### 3.1 求职目标

- 为游戏客户端开发实习准备第二个作品集项目。
- 与《背包幸存者》形成互补：一个主打玩法闭环与系统深度，一个主打客户端技术栈广度和工程链路。
- 面向米哈游、腾讯、网易、字节等头部游戏公司的客户端岗位，展示 Unity、C#、网络同步、资源加载、动作战斗和工程工具能力。

### 3.2 技术目标

- 完成一个最小但完整的联机动作 RPG 技术纵切片。
- 客户端与服务端分层明确，至少支持本机或局域网 2 个客户端联机演示。
- 具备可解释的网络同步方案、异步加载流程、动作战斗结构和性能验证记录。
- 所有关键系统都能讲清楚“为什么这样设计、怎么验证、有哪些限制、后续如何扩展”。

### 3.3 学习目标

- 从单机 Gameplay 开发推进到联网客户端工程。
- 补网络、OS、C++、资源管理、图形渲染、Lua / 热更新等长期学习路线中的实战切入口。
- 建立第二项目的持续复盘材料，为后续简历、面试和知识库沉淀服务。

## 4. 项目边界

### 4.1 MVP 必须完成

MVP 只追求一条完整链路：

```text
启动客户端
  -> 注册 / 登录
  -> 进入大厅
  -> 创建或加入房间
  -> 准备并开始
  -> 异步加载训练场
  -> 2 个客户端进入同一战斗场景
  -> 同步移动、朝向、普攻、技能、受击、血量
  -> 结算
  -> 返回大厅
```

### 4.2 暂不做的内容

以下内容不进入第一版 MVP，避免项目膨胀：

- 大世界开放地图；
- 完整剧情、任务和 NPC 系统；
- 大规模多人同屏；
- 完整装备、养成、背包经济系统；
- 复杂 Boss 副本；
- 完整商业级账号安全；
- 完整线上部署与运维；
- 一开始就接入复杂热更新或完整 Lua 战斗逻辑。

这些可以作为后续加分扩展，而不是立项初期的硬目标。

## 6. 技术选型

| 方向 | 初始选择 | 理由 | 后续可扩展 |
|---|---|---|---|
| 客户端引擎 | Unity + C# | 延续现有优势，快速进入客户端工程验证 | 后续可补 Shader、URP、自定义工具 |
| 渲染管线 | URP | 适合轻量动作 Demo 和可控性能验证 | 后续补基础后处理、Shader、技能特效 |
| 输入系统 | Unity Input System | 延续第一个项目经验 | 可补手柄输入和按键重绑定 |
| 摄像机 | Cinemachine | 快速搭建第三人称镜头 | 可补锁定镜头和震屏 |
| 资源管理 | Addressables | 展示异步加载和资源组织能力 | 远程 Catalog、版本检查、失败重试 |
| 服务端 | C# / .NET 8 Console 或 ASP.NET Core | 降低语言切换成本，专注网络和协议 | 后续可接 SQLite、Docker、一键启动 |
| 网络协议 | WebSocket 起步 | 调试简单，适合演示请求 / 推送 / 状态广播 | 后续研究 KCP / UDP / 预测 / 插值 |
| 协议格式 | JSON 起步 | 可读性强，便于调试和展示 | 后续替换 MessagePack / Protobuf |
| 配置数据 | ScriptableObject + JSON / CSV | 兼顾编辑器配置和运行时数据 | 后续接配置热加载或 Lua |
| 热更新 | 第一版只做数据热加载 | 避免初期被 Lua 拖垮 | 后续接 xLua 小逻辑热更 |

## 7. 系统模块规划

### 7.1 客户端模块

| 模块 | 职责 | MVP 内容 |
|---|---|---|
| App / Boot | 启动流程和全局状态 | 初始化配置、网络模块、资源系统 |
| Login | 登录界面和账号流程 | 注册、登录、错误提示、Token 保存 |
| Lobby | 大厅和房间 UI | 创建房间、加入房间、准备、开始 |
| Loading | 异步加载流程 | 加载进度、失败重试、场景切换 |
| Network | 网络连接和协议分发 | WebSocket 连接、收发包、心跳、重连提示 |
| Character | 角色控制 | 移动、朝向、动画状态、基础属性 |
| Combat | 战斗逻辑 | 普攻、闪避、技能、受击、伤害、死亡 |
| Sync | 网络同步表现 | 远端玩家插值、事件同步、血量同步 |
| UI | 游戏内 HUD | 血条、技能 CD、网络状态、结算面板 |
| Debug | 调试工具 | 网络日志、状态面板、延迟模拟、GM 指令 |

### 7.2 服务端模块

| 模块 | 职责 | MVP 内容 |
|---|---|---|
| AccountServer | 账号管理 | 注册、登录、Token 生成和校验 |
| LobbyServer | 大厅和房间 | 创建房间、加入房间、准备状态、开始游戏 |
| BattleServer | 战斗房间 | Tick 驱动、状态广播、玩家输入处理 |
| Protocol | 协议定义 | 请求 / 响应 / 广播结构 |
| Persistence | 简单持久化 | MVP 可用内存字典；后续接 SQLite |
| Debug | 服务端日志 | 连接、协议、房间、战斗状态输出 |

## 8. 网络同步初始方案

MVP 不追求一开始就实现复杂预测和回滚，先建立可讲清的状态同步链路。

### 8.1 初始同步模型

```text
客户端采集输入 / 行为
  -> 发给服务端
  -> 服务端按 Tick 更新或校验状态
  -> 服务端广播快照 / 事件
  -> 客户端插值显示远端玩家
```

### 8.2 MVP 同步内容

- 玩家进入 / 离开房间；
- 位置、朝向、移动状态；
- 普攻事件；
- 技能释放事件；
- 受击、血量、死亡；
- 战斗开始和结算。

### 8.3 后续扩展

- 快照插值参数可视化；
- 延迟 / 丢包模拟；
- 客户端预测；
- 服务端权威校验；
- KCP / UDP 版本；
- 战斗回放或包日志对比。

## 9. 动作战斗设计范围

### 9.1 MVP 动作

- 第三人称移动；
- 镜头跟随；
- 目标锁定；
- 普攻 3 连段；
- 闪避；
- 1 个主动技能；
- 受击、硬直、击退；
- 血量和死亡。

### 9.2 技术重点

- 动画状态机和输入缓冲；
- 攻击判定 HitBox / HurtBox；
- 技能配置数据；
- 战斗事件同步；
- 本地手感与网络表现的边界；
- 技能特效的异步加载与对象池复用。

### 9.3 不追求的内容

- 复杂动作取消；
- 大量角色；
- 高复杂 Boss；
- 商业级动作手感；
- 完整元素反应。

## 11. 迭代模块规划

本项目不按固定周数硬排期，而按模块迭代推进。每个迭代必须有可运行、可截图、可复盘的验收物。

| 迭代 | 目标 | 验收标准 |
|---|---|---|
| 迭代 0：项目骨架与通信验证 | Unity 客户端和 C# 服务端能连起来 | 客户端能连接服务端并完成 Ping / Pong |
| 迭代 1：账号登录闭环 | 做出商业客户端入口 | 注册、登录、Token、错误提示和进入大厅可演示 |
| 迭代 2：大厅房间闭环 | 多人进入同一房间 | 创建、加入、准备、开始战斗可演示 |
| 迭代 3：异步资源与场景流 | 从大厅加载到战斗场景 | Addressables 加载进度、资源加载和 Ready 上报可演示 |
| 迭代 4：本地动作战斗原型 | 单人动作可玩 | 第三人称移动、锁定、普攻、闪避、技能和受击可演示 |
| 迭代 5：基础网络同步 | 两个客户端看到彼此 | 位置、朝向和远端插值同步可演示 |
| 迭代 6：战斗事件同步 | 攻击、受击、血量和结算同步 | 联机战斗最小闭环可演示 |
| 迭代 7：调试与弱网工具 | 让同步问题可观察 | 协议日志、RTT、延迟 / 丢包模拟、GM 指令可使用 |
| 迭代 8：性能与交付 | 变成可展示作品 | Profiler、加载耗时、GC Alloc、Windows Build、演示视频和 README 完成 |
| 迭代 9：加分扩展 | 选择少量高价值扩展 | 从 SQLite、二进制协议、KCP、xLua、Boss、Shader 中选 1-2 个 |

详细拆解见：[迭代模块规划](迭代模块规划.md)。

## 14. 风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 范围膨胀 | 想同时做动作、联网、热更、Boss、剧情、装备 | MVP 只保留登录 -> 大厅 -> 加载 -> 联机战斗 -> 结算 |
| 网络同步难度过高 | 预测、回滚、KCP 一开始拖慢进度 | 先做 WebSocket + 快照广播 + 插值，后续再扩展 |
| 动作手感耗时 | 为了动作质量无限打磨 | MVP 只要求可解释、可演示，不追求商业级手感 |
| 服务端喧宾夺主 | 把时间花在后端框架和部署 | 服务端只服务客户端展示，优先协议清晰 |
| 资源加载变成空壳 | 只有 loading bar，没有真实资源组织 | 至少让角色、场景、技能特效走异步加载链路 |
| 证据不足 | 功能做了但没有记录 | 每阶段必须留下运行截图、日志、Profiler 或演示视频 |
